2. CURRENT RUNTIME ARCHITECTURE (DEPLOYMENT / DEV)
--------------------------------------------------------------------------------

- Client: Next.js (e.g. Vercel in production per docs/deployment.md).
- Backend: FastAPI on EC2 (or local uvicorn), talking to PostgreSQL and Redis.
- ML: Separate container/service on port 8001, used for insights-style workloads.

Target evolution: modular monolith first (clear modules inside server/ + client/),
optional extraction to more microservices later under pressure — not a big-bang
split on day one.

3. KNOWN GAPS IN THE CURRENT CODEBASE (PRE-PHASE 0)
--------------------------------------------------------------------------------

These are specific issues found during codebase review that Phase 0 must fix
before new modules are built:

1. Auth context is incomplete: dependencies.py only resolves user_id from
   the JWT. There is no business_id in the token context, which means routers
   currently trust client-supplied business IDs for tenant scoping.

2. Tenant isolation is not enforced by middleware: the reservations router
   does not verify that the authenticated user belongs to the business whose
   data is being accessed. This is a security gap.

3. Staff roles are coarse (owner/manager/staff strings). The plan moves to
   permission-based RBAC — the migration path must be planned before new
   modules rely on the old role system.

4. No standardized error JSON format across routers — each returns errors
   differently today.

5. No require_module() guard exists anywhere yet.

4. PRODUCT DIRECTION (SUMMARY)
--------------------------------------------------------------------------------

Move from a reservation-centric client-server + ML setup to a multi-module
platform for service businesses:

  - Reservations       (existing — refine and harden)
  - Waitlist / Queue   (new, lightweight — bridge between reservations and ordering)
  - Ordering           (QR / customer self-order; kitchen/bar + waiter ticket flow)
  - Inventory          (restaurant inventory, not generic cloud storage)
  - Data analysis & ML-based insights across enabled modules

Client-facing features that make the platform presentable:
  - Business onboarding wizard (guided setup for new signups)
  - Embeddable booking widget (iframe/JS snippet for business websites)
  - Rich public business profile page (beyond booking-only)
  - Two-way Google Calendar sync (leverages existing OAuth infrastructure)
  - SMS / WhatsApp reservation reminders (alongside existing email)
  - Pricing / plan display page (visible to clients even before billing ships)

Requirements:
- One business = one tenant; one login per business (no multi-business user
  in this phase).
- Businesses subscribe to modules independently (e.g. only inventory + insights).
- One primary web dashboard; routes and nav depend on enabled modules.
- Mobile/tablet apps later; same APIs and entitlement model.
- Real-time transport: WebSockets (decided — not deferred). Infrastructure
  introduced in Phase 2 alongside ordering, hardened in Phase 4.

Billing: per-module and per-location pricing is a later phase; for now build
modules and entitlements without full commercial plumbing. A static pricing
page should be visible by Phase 1 for client demos.

5. AGREED CLARIFICATIONS (SCOPE)
--------------------------------------------------------------------------------

1) Ordering
   - Customer self-order via QR + menu.
   - Internal: communication / workflow between kitchen/bar tickets and waiters
     (ticket board, statuses).

2) Waitlist / Queue
   - Customer scans QR at the door to join a digital queue.
   - Staff sees live queue on dashboard; can call next, seat, or remove.
   - Lower complexity than full ordering; serves as a real-time proof of concept
     before Phase 2.

3) Inventory
   - Restaurant inventory (ingredients, stock movements, par levels, etc.),
     not warehouse WMS unless extended later.

4) Pricing / billing
   - Defer full implementation; still implement module enablement flags in data
     model and API. A visible pricing/plan page (even static) ships in Phase 1.

5) Tenancy
   - One business per login; each business is a tenant.

6) Real-time transport
   - Decision locked: WebSockets via FastAPI WebSocket endpoints + a thin
     client hook (useWebSocket). SSE is acceptable for read-only push (e.g.
     notifications) but WebSockets are the primary choice for ticket boards
     and queue state.

7) Location / multi-location
   - Decision locked: location_id added to schema in Phase 0 (nullable),
     on orders, inventory rows, and queue entries. Single-location businesses
     ignore it. Retrofitting later touches every table and query — adding it
     now costs almost nothing.

8) Embeddable widget
   - The existing public /reserve/[business] route is the content; the widget
     is a thin iframe wrapper + JS snippet generated per business. Ships in
     Phase 1.

9) Calendar sync
   - google_oauth_tokens table already exists. Two-way Google Calendar sync
     for staff appointments/reservations is a Phase 1 extension of existing
     infrastructure, not new work.

10) Notifications
    - Email notifications already exist. SMS/WhatsApp (via Twilio or similar)
      added in Phase 1 as an additional channel for reservation reminders.
      Architecture: notification_service dispatches to multiple providers;
      business configures which channels are active.

6. ROLES & UI STRATEGY (ORDERING / STAFF)
--------------------------------------------------------------------------------

- Customer ordering: separate UX from staff (public/menu/cart flow; often
  unauthenticated or session-token based) — separate routes/layout, can live
  in the same Next.js app (e.g. route groups).

- Customer queue: same pattern — public QR scan flow, no account required.
  Session token identifies the customer in the queue.

- Staff (server, kitchen/bar, admin): one dashboard shell with role + permission
  checks; kitchen vs bar often modeled as stations or item tags + filtered
  ticket boards, not necessarily separate apps.

- Prefer permission names (can_manage_menu, can_bump_tickets, can_manage_queue,
  can_view_inventory, ...) over only job titles. The existing owner/manager/staff
  string roles become a grouping shortcut, not the source of truth for access.

--------------------------------------------------------------------------------
7. FRONTEND STRATEGY
--------------------------------------------------------------------------------

- One client/ Next.js app is realistic and optimal for starters.
- Organize by module inside the repo: e.g. app/(customer)/..., app/business/...,
  components/ordering/, components/inventory/, components/queue/, lib/api/ordering.ts, etc.
- Code-split heavy modules; split deployables/repos only if team/release or
  compliance needs demand it.
- Public-facing routes (booking widget, queue join, menu/cart) live in separate
  route groups from the authenticated dashboard, sharing the same Next.js app.

8. PHASE 0 — FOUNDATION (DETAILED)
--------------------------------------------------------------------------------

Goal: safe growth — fix known gaps, establish boundaries, tenant isolation,
module gates, conventions — without shipping new product modules.

A) Fix known auth and tenant gaps (critical — do first)
   - Add business_id to JWT claims; update get_current_user to resolve
     and attach the user's associated business_id.
   - Add get_current_business dependency that reads from token context,
     not from the request body or path params.
   - Audit all existing routers: any route that accesses business data must
     filter by the authenticated business_id, not a client-supplied value.
   - Add require_roles(...) dependency.

B) Module boundaries (docs + folders)
   - Name modules: reservations, queue, ordering, inventory, insights, platform
     (auth/tenant/entitlements).
   - Convention: per-module routers, services, schemas, models; shared only in
     platform/common with rules (no domain logic leaking into generic utils).
   - Rule: reservations code does not import ordering services directly;
     cross-domain via public service calls, events, or a thin integration layer.

C) Tenant model
   - All domain rows scoped with business_id (consistent — not tenant_id).
   - Add location_id (nullable UUID, FK to a new locations table) to:
     reservations, any future orders, inventory rows, queue entries.
     Single-location businesses leave it null; multi-location businesses set it.
   - Every query filters by tenant from authenticated context.

D) Entitlements (modules) — server-side first
   - Add enabled_modules JSONB column (or child table) to businesses.
   - Stub "all enabled" in seed data for development.
   - require_module("ordering") dependency on all module routes; returns 403
     with stable error code MODULE_DISABLED.

E) API conventions
   - Standardize error JSON across all routers: { code, message, details }.
   - Consistent pagination pattern (cursor + limit).
   - Idempotency key header helper (for ordering and future payment flows).

F) Events (minimal)
   - Envelope: event_type, version, occurred_at, business_id, location_id,
     payload, correlation_id.
   - Publisher abstraction: publish(event) — stdout or outbox table now,
     Redis Streams in Phase 4, without rewriting callers.

G) Real-time transport decision (locked in Phase 0, infrastructure in Phase 2)
   - Document the chosen transport (WebSockets) and expected usage patterns.
   - Define the WebSocket connection lifecycle: auth handshake, room/channel
     model (one channel per business + module), reconnect strategy.
   - Do not build yet — just spec and agree so Phase 2 doesn't start blind.

H) Observability
   - Structured logs: business_id, user_id, request_id per request (FastAPI
     middleware).

I) Tests
   - At least one integration test: authenticated user cannot read another
     tenant's data (the current codebase has no such test).
   - Add test: require_module returns 403 when module is disabled.

J) Permissions migration plan
   - Document how existing owner/manager/staff roles map to the new permission
     set. The old roles stay as a convenience grouping; permissions become the
     enforcement layer. Plan the migration before Phase 2 needs can_bump_tickets.

Phase 0 exit criteria:
   - JWT contains business_id; all routers enforce tenant from context.
   - Clear module "homes" for new code.
   - location_id column exists on relevant tables (nullable).
   - Server-side module guards exist and are tested.
   - Single event shape + publish path documented and implemented.
   - Standardized error format across all existing routers.
   - Existing reservation flows still work (regression tests pass).

9. PHASE 1 — ENTITLEMENTS + DYNAMIC SHELL + CLIENT-FACING FOUNDATION
--------------------------------------------------------------------------------

Goal: make the platform presentable to potential clients and ready for new
modules. This phase ships visible, demo-able features alongside the technical
entitlements work.

A) Entitlements API + dynamic dashboard
   - GET /me/context: user, business, role, permissions, enabled_modules,
     location(s).
   - Frontend: nav and routes driven by entitlements; guard deep links.
   - Disabled module: proper 403 / "module disabled" UX with upgrade prompt.
   - Seed toggles modules per tenant for testing.

B) Business onboarding wizard
   - Step-by-step flow triggered on first login after registration:
     1. Business profile (name, address, logo, description)
     2. Operating hours setup
     3. Add first service type (or "skip for now")
     4. Enable modules selection (visual, not billing yet)
     5. Invite first staff member (optional)
   - Without this, new client demos start on an empty dashboard with no
     guidance — this is the difference between a convincing demo and a
     confusing one.

C) Rich public business profile page
   - Extend /reserve/[business] to be a full business page:
     about, photos, hours, tags, reviews placeholder, book button.
   - Businesses effectively get a mini-website on the platform.
   - Increases the pitch: "your business gets a presence on Slotera."

D) Embeddable booking widget
   - A JS snippet (or iframe) generated per business from their dashboard.
   - Renders the existing booking flow in a modal overlay on any external site.
   - Pitch: "keep your own website, just paste this snippet to add booking."
   - Implementation: thin wrapper around /reserve/[business]; postMessage for
     cross-origin events (confirmation, close).

E) Two-way Google Calendar sync
   - google_oauth_tokens table and OAuth flow already exist (used for Meet).
   - Extend to sync confirmed reservations to the business's Google Calendar.
   - Staff can see reservations alongside personal events.
   - No new infrastructure needed — extend existing google_oauth_service.

F) SMS / WhatsApp notifications (alongside existing email)
   - Add SMS/WhatsApp as notification channels via Twilio (or equivalent).
   - Notification service already exists; add provider abstraction so business
     can configure active channels (email, SMS, WhatsApp) from settings.
   - Use case: reservation reminders 24h and 1h before; queue position updates.

G) Pricing / plan display page
   - Static page showing module tiers and what each includes.
   - No payment processing yet — "contact us" or waitlist CTA.
   - Essential for client demos: they need to understand the commercial model.

H) Marketing page update
   - Update the homepage to reflect the full multi-module platform vision,
     not just reservations.
   - Add sections for each module (reservations, ordering, inventory, insights).

Exit: toggling modules in DB changes UI + API access. A new business signing
up can complete onboarding and have a public profile + booking widget in under
10 minutes. The platform is presentable to a potential client.

10. PHASE 1.5 — WAITLIST / WALK-IN QUEUE MVP  [COMPLETE]
--------------------------------------------------------------------------------

Goal: ship a lightweight real-time feature that is compelling for restaurant
demos without the full complexity of ordering. Proves the WebSocket path before
Phase 2 relies on it.

- Customer flow: scan QR at the door → enter name + party size → receive
  estimated wait time and position in queue.
- Staff flow: live queue board in dashboard — see all waiting parties, notify
  (SMS), accept (seat directly), mark as seated, remove no-shows.
- Real-time: WebSocket channel per business (first production use of the
  transport decided in Phase 0). Queue state pushed to all connected staff.
- No customer account required — anonymous session token identifies the party.
- Models: queue_entries (business_id, location_id, session_token, name,
  party_size, status, joined_at, called_at, seated_at).
- Notification: optional SMS when party is called ("Your table is ready!").
- In-app notifications: queue_join / queue_leave / queue_called / queue_accepted
  events fan out to all business staff via notification_service.

Why this phase exists:
- Ordering (Phase 2) is significantly more complex than reservations. Rushing
  into it without a smaller real-time proof-of-concept is risky.
- The queue feature is highly visible in demos ("watch what happens when
  someone scans this QR...") and directly useful for restaurants.
- It validates the WebSocket infrastructure before Phase 2 depends on it.

Exit: DONE. A party scans a QR, joins the queue, and sees their position update
live as staff manage the board. Staff dashboard shows the live queue with
controls. Staff receive in-app toast notifications for queue events.

Implementation notes (non-obvious decisions):
- WebSocket JWT auth: JWT is in an httpOnly cookie, unreadable by JS. The
  useQueueSocket hook fetches a short-lived token from /api/ws-token (Next.js
  server route) before connecting. FastAPI WS endpoint validates via jose.jwt.
- queue_service.remove_by_token returns QueueEntry | None (not bool) so the
  router can use entry.name / entry.party_size in the leave notification body.
- Notification toast deduplication uses a knownIdsRef (Set<string>) in
  NotificationTrigger so already-seen notifications are never re-toasted.
- Staff-initiated actions (notify/accept) pass exclude_user_id=current_user.id
  to avoid self-notifications.
- Migrations 005 and 006 were renamed after being applied (see CLAUDE.md).

11. PHASE 2 — ORDERING MVP
--------------------------------------------------------------------------------

Goal: full QR-based customer ordering with real-time kitchen/bar ticket board.
WebSocket infrastructure proven in Phase 1.5 is extended here.

- Models: menus, categories, items, modifiers, modifier_groups, orders,
  order_line_items, order_status_timeline.
- All rows scoped with business_id and location_id.
- Customer flow: QR → menu → cart → place order (anonymous session or account).
- Idempotency key on order placement (planned in Phase 0, implemented here).
- Staff ticket board:
  - Kitchen and bar views filtered by routing tag on items.
  - Statuses: received → preparing → ready → served.
  - Audit log: who changed status and when.
- Real-time: extend Phase 1.5 WebSocket infrastructure to order channels.
  Staff board updates instantly when an order is placed or status changes.
- Operational basics: item availability toggle, routing tags, order notes,
  estimated prep time display.
- require_module("ordering") gate on all ordering routes.

Exit: customer order appears on the staff board in near real-time; staff
status updates propagate live to customer-facing order status view.

12. PHASE 3 — INVENTORY MVP  [COMPLETE]
--------------------------------------------------------------------------------

- Models: inventory_items (name, unit free-text, current_quantity denormalized,
  par_quantity nullable, cost_per_unit), stock_movements (receive/adjust/waste,
  quantity_delta, alert_triggered), menu_item_ingredients (recipe stub FK only).
  All rows scoped with business_id and location_id.
- Operations: receive stock (+delta), waste (-delta, auto-negated), manual adjust.
- Par levels: set minimum stock; alert when breached.
- Low-stock alert: notify_business_staff fires on par breach; alert_triggered=true
  set on the causative stock_movements row as audit record.
- Dashboard: item list (low-stock first), quantity badges (red/green), movement
  dialog, movement history sheet, amber low-stock alert strip.
- require_module("inventory") gate on all inventory routes.

Implementation notes (non-obvious decisions):
- current_quantity is denormalized on inventory_items, updated per movement.
  recompute_quantity_from_movements() provides a SUM(quantity_delta) reconciler.
- waste movements always store a negative delta; the service negates the
  user-supplied value so staff always enter a positive number.
- alert_triggered on stock_movements is the audit record of when alerts fired —
  no separate low_stock_alerts table.
- menu_item_ingredients stub exists for Phase 5/6 recipe wiring; nothing reads
  or writes it via the API in Phase 3.

Exit: DONE. Staff can add inventory items, record stock movements, set par
levels, and see low-stock items highlighted in the dashboard. Staff receive
in-app notifications when stock drops below par.

13. PHASE 4 — EVENT STREAM + REAL-TIME HARDENING
--------------------------------------------------------------------------------

Goal: replace ad-hoc DB polling and point-to-point WebSocket push with a
structured event pipeline. Harden the real-time infrastructure built in
Phases 1.5 and 2.

- Redis Streams for domain events (reservation.created, order.status_changed,
  inventory.low_stock, queue.party_called, etc.).
- Typed consumers: live UI projection consumer, analytics ingestion consumer,
  notification consumer.
- Replace Phase 1.5 / Phase 2 direct WebSocket push with event-driven push:
  consumers read from streams and push to connected WebSocket clients.
- Retries and dead-letter handling for failed consumers.
- Version event schemas; document compatibility policy.
- Backpressure handling: define what happens when consumers fall behind.

Exit: all domain events flow through one pipeline; WebSocket clients receive
updates from stream consumers rather than ad-hoc direct pushes.

14. PHASE 5 — INSIGHTS (SURFACE EXISTING ML + OPERATIONAL ANALYTICS)
--------------------------------------------------------------------------------

Goal: make the ML work already done in the ml/ service visible in the
dashboard. Do not build new models yet — surface what exists first.

A) Surface existing ML outputs
   - Customer segmentation (RFM) → "Customer Insights" page with segment
     badges and loyalty indicators per customer.
   - Cancellation prediction → flag high-risk reservations in the dashboard.
   - 7-day demand forecast → staffing suggestion on the overview page.
   - These all already run in the ML service at /results/*. Work is mostly
     frontend + wiring, not new modeling.

B) Operational KPIs from events (from Phase 4 pipeline)
   - Reservations: no-show rate, occupancy by time slot.
   - Ordering: average prep time, peak hours, top items.
   - Inventory: stock velocity, waste frequency, low-stock incidents.
   - Scheduled aggregations written to a summary table; dashboard reads from it.

C) Module-gated insight pages
   - Insights only visible for enabled modules.
   - require_module("insights") gate.

Exit: each enabled module has a small set of trustworthy operational metrics.
Existing ML model outputs are visible in the dashboard without new training.

15. PHASE 6 — ML V2 (TARGETED IMPROVEMENTS)
--------------------------------------------------------------------------------

Goal: improve and extend ML capabilities now that there is richer event-derived

- Demand / stock forecasting with ordering + inventory data as additional features.
- Reorder suggestions (inventory) driven by forecast + par levels.

- Feedback mechanism in UI: staff can mark a recommendation as helpful/unhelpful

- ML service remains separate (already is); event-derived features flow from
  Phase 4 pipeline.

honest uncertainty indicators. At least one recommendation has a measurable
feedback loop.
