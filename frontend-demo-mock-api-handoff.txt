WHAT ALREADY EXISTS — READ THIS BEFORE DESIGNING ANYTHING
────────────────────────────────────────────────────────────────────────────────

1. THERE IS ALREADY A PARTIAL, UNDOCUMENTED MOCK LAYER. Do not build a second
   one alongside it without deciding what happens to the first.

     client/lib/api-mock.ts    162 lines, 15 functions
     client/lib/mock-data.ts   711 lines
     client/lib/api.ts         `const USE_MOCK = process.env.NEXT_PUBLIC_USE_MOCK_API === "true"`
                               and ~18 `if (USE_MOCK) return mock.x()` branches

   Its reach is small. It only short-circuits the SERVER-side helpers in
   `client/lib/api.ts` (~20 functions). The browser-side client
   `client/lib/client-api.ts` has ~202 functions and NONE of them are mocked.
   Auth in mock mode returns no token and no user, so nothing under `/business`
   is reachable. No document in AGENTS.md, docs/, README.md or CHEATSHEET.txt
   mentions it. Check whether its fixtures even still match current types — it
   predates much of the current product.

   Your plan must say what happens to it: replaced, absorbed, or deleted. Leaving
   two mock mechanisms in the tree is not an acceptable outcome.

2. THE NETWORK SHAPE — this is the most important fact for the design.

   Almost ALL traffic already leaves the frontend through ONE configurable
   backend base URL (`API_INTERNAL_URL`, falling back to `NEXT_PUBLIC_API_URL`,
   falling back to `http://localhost:8000`):

     - Browser HTTP never calls the backend directly. `client/lib/client-api.ts`
       fetches same-origin `/api/backend/...` (a rewrite in
       `client/next.config.ts`, unauthenticated) and `/api/proxy/...` (a route
       handler, `client/app/api/proxy/[...path]/route.ts`, which reads the
       httpOnly `rk-token` cookie and adds the Authorization header).
     - Server components call through `client/lib/api.ts` / `client/lib/api-client.ts`.
     - A handful of route handlers forward too: `client/app/api/auth/*`,
       `client/app/api/invite/accept`, `client/app/api/ws-token`.
     - `client/lib/ml-api.ts` reads the same variables.

   THE EXCEPTION is WebSockets. The four hooks
   (`client/hooks/use-{queue,order,tab,floor-plan}-socket.ts`) connect from the
   browser straight to `NEXT_PUBLIC_API_URL` rewritten to ws:// / wss://.

   What this implies, for you to confirm or refute: a mock that speaks the
   backend's HTTP contract at a base URL could need NO call-site changes at all,
   whereas the existing in-function `if (USE_MOCK)` approach would need to fork
   200+ functions. Evaluate both honestly — and any third option you find — and
   say which you chose and why.

3. THE CONTRACT IS DISCOVERABLE. FastAPI serves `/openapi.json` outside
   production (`server/app/main.py:172-174`). The seeded demo tenant — Volt &
   Vine, slug `volt-and-vine` — is the obvious source of fixture data, and it is
   what the user already knows and has been testing against. Consider whether
   fixtures should be RECORDED from a seeded local stack rather than hand-written:
   recorded responses match the real contract; hand-written ones drift from it
   silently. If you propose recording, the recorder must be a repeatable script,
   not a one-off.

────────────────────────────────────────────────────────────────────────────────
THE HARD PROBLEMS — THE PLAN MUST ANSWER EACH ONE
────────────────────────────────────────────────────────────────────────────────

A. SIGNING IN. `client/proxy.ts` decides access by decoding the `rk-token` JWT
   payload (it does not verify the signature — the backend does). So the demo
   needs a token of the right shape carrying the right `user_type` and `sub`, or
   every `/business` route redirects to login. How does a demo visitor get in?
   A one-click "enter the demo" is likely better than a password form — and see
   the credential constraint below before you consider any shared password.
   Also decide: can a visitor see the product as different roles (owner vs a
   bartender)? Roles gate nav, pages and capabilities throughout.

B. MUTATIONS ON A STATELESS HOST. Vercel functions do not keep memory between
   invocations or across instances. A mock that "accepts" a booking and then
   forgets it on the next request produces a demo that looks broken. Options
   range from read-only (every write shows a clear "not saved in the demo"
   state), to per-visitor state held client-side, to state that lives for one
   session. Recommend one. Whatever you pick must be honest on screen — a demo
   must never show "saved" for something that will vanish without saying so.

C. LIVE BOARDS AND THE OFFLINE ALARM. There is no WebSocket server in a
   Vercel-only deployment. The queue board, ticket board, tabs and floor map all
   open sockets, and `client/components/offline-bar.tsx` is the ONE critical
   alarm in the system: a persistent red flashing band saying the board is "Not
   updating". In a demo with no socket server, every live board would show that
   alarm permanently. That is unacceptable in a demo AND it must not be
   "fixed" by weakening the alarm for real deployments. Read the header comments
   in `offline-bar.tsx` and `server/app/core/heartbeat.py` before deciding. The
   alarm's behaviour against a real backend must be byte-for-byte unchanged.

D. TIME. Seed and fixture data is dated. A demo showing "tonight's bookings" from
   a fixed date will look dead a week after it is deployed. Decide how dates are
   kept relative to the visitor's current day, in the venue's timezone
   (Europe/Berlin), without scattering date arithmetic across the fixtures.

E. COVERAGE. There are 46 `page.tsx` routes. Do not attempt all of them at full
   fidelity. Recommend a scope — the natural spine is the service loop defined
   by the `run-crowbar-service-loop` skill (book, assign, seat, order by QR or
   staff, fulfil, stock deduction, record external settlement, close, guest and
   cost history) plus the public guest pages (`/reserve`, `/menu`, `/order`,
   the queue join page). Everything outside the chosen scope must degrade to an
   honest, designed "not available in the demo" state — never a crash, never a
   spinner that never resolves, never the generic error boundary.

F. THINGS THAT MUST NEVER HAPPEN FROM A DEMO. No email, no SMS, no provider call
   of any kind, no call to any ML service. The ML-backed insights surfaces need an
   answer too — see how they already represent "no model" honestly (a recent pass
   made ML honesty end to end) and reuse that rather than faking predictions.

G. NEVER CONFUSABLE WITH THE REAL THING. A visitor must always be able to tell
   they are in a demo. And the reverse matters more: demo mode must be impossible
   to switch on by accident against a real backend or in a real venue
   deployment, and a mock token must be worthless against a real API (it will be,
   if the backend verifies signatures — confirm it rather than assuming). Note
   that `NEXT_PUBLIC_*` variables are inlined at BUILD time: the demo is a build
   decision on Vercel, not a runtime toggle. Make the plan say which variables
   the Vercel project needs, but see OUT OF SCOPE — you do not set them.

H. CONTRACT DRIFT. The backend will keep changing while the demo sits still. Say
   how anyone would find out the mock no longer matches the API — ideally a check
   that fails, not a document someone must remember to read.

DEV.SH DEMO MODE
────────────────────────────────────────────────────────────────────────────────

`scripts/dev.sh` today: port preflight for 8000 and 3000; `docker compose up -d
--build` (Postgres, Redis, ML); venv + pip install; `createdb`; migrations (and
seed when `SEED_DATA=true`); npm install; uvicorn on 8000 and `npm run dev` on
3000; waits for both ports; prints a banner. Options are currently environment
variables: `SEED_DATA=true`, `KILL_STALE=true`.

Add a demo mode that:

  - Starts ONLY what the demo needs. No Docker, no venv, no pip, no migrations,
    no uvicorn, no ML. It must work on a machine where Docker is not running and
    `server/venv` does not exist — test exactly that.
  - Preflights only the ports it actually uses, with the same
    `require_free_port` / `KILL_STALE` behaviour as the normal path.
  - Accepts a flag to point the frontend at a mock API URL — the local mock by
    default, or a remote one (for example the deployed demo's mock) when given.
    The user asked for a flag. Reconcile that with the script's existing
    environment-variable style in whatever way is least surprising, and make sure
    `SEED_DATA` / `KILL_STALE` keep working exactly as they do now.
  - Rejects nonsense early: an unknown flag, or a mock-URL flag without demo
    mode, fails with a one-line usage message rather than half-starting.
  - Prints a banner that says plainly this is the demo and which API it is
    talking to.
  - Cleans up its own processes on Ctrl+C using the existing `cleanup` trap.

THE NORMAL PATH MUST NOT CHANGE. `./scripts/dev.sh` with no flag behaves exactly
as it does today. Verify it, do not assume it.

Beware one trap: Next reads `NEXT_PUBLIC_*` at build/dev-server start and
`client/.env.local` may already set `NEXT_PUBLIC_API_URL`. Make sure demo mode
actually wins over a developer's existing env file WITHOUT editing or deleting
that file.

Document demo mode where the dev commands are already documented (CHEATSHEET.txt
and wherever AGENTS.md routes dev workflow). Fix any stale lines you find there.

CONSTRAINTS THAT APPLY THROUGHOUT
────────────────────────────────────────────────────────────────────────────────

NO PLAINTEXT PASSWORDS. `scripts/export-portfolio.sh` copies an allowlist of
tracked files — `client/lib`, `client/app`, `client/components`, `server/db/seeds`
and more — and FAILS the export if public content matches
`password123([^0-9]|$)`. Only `server/db/migrate.py` and the export script itself
are exempt. Demo fixtures, mock handlers and dev.sh all ship in that export. Do
not put a demo password, a real hash of a known password, or a real signing
secret in any of them. Test and automation code reads `DEMO_ADMIN_PASSWORD` from
the environment — no literal, no fallback. If the demo ships as new files under a
path the export does NOT already cover, say so in your report rather than
silently editing the allowlist; if you do edit it, run the export into a scratch
directory and confirm it passes.

COMPLIANCE BOUNDARY — ABSOLUTE. Crowbar is preparing a supervised, NON-FISCAL
pilot at one German bar. The venue's own compliant register remains the payment
and fiscal authority; Crowbar only records that a tab was "settled externally".
No row, column, log line, test name, fixture or user-visible string may say
"paid", "payment processed", or "revenue". This binds fixture data and demo copy
as tightly as product code — a demo is the most-shared surface this product has.
Use the `write-crowbar-operational-copy` skill for any string you add.

PRIVACY. Fixture people must be obviously fictional (`@example.com`, reserved
555 numbers — the seed already does this). No real names, addresses, or the
developer's own details, including anything left in the local database from
manual testing.

DESIGN CONTRACT — RULE ZERO. `docs/DESIGN.md`: no colour, size, spacing value,
radius or duration may enter that `:root` in `client/app/globals.css` does not
declare. Use the `frontend-design` skill for the demo indicator and the "not in
the demo" state. Both grep gates over `client/` must be no worse than now:

    rg '#[0-9a-fA-F]{3,8}\b' client/

VERIFICATION — GREEN TESTS ARE NOT ENOUGH
────────────────────────────────────────────────────────────────────────────────

A live walk is the definition of verified here. For the demo that means a
production build, not just the dev server — a Vercel deployment runs `next build`
and `next start` semantics, and build-time env inlining is exactly where a demo
breaks. Run `npm run build` with the demo configuration and walk the result.

With Docker STOPPED and the API NOT running:
  - `./scripts/dev.sh` in demo mode starts, and every journey in the approved
    scope works end to end, following the `run-crowbar-service-loop` skill's
    spine as far as the approved scope reaches.
  - Every out-of-scope route shows the designed "not in the demo" state. Walk all
    46 routes and list the result for each — do not sample.
  - No live board shows the offline alarm.
  - The browser network log shows no request leaving for anything but the
    frontend's own origin (and the mock's, if it is separate).

Then with the normal stack running (`./scripts/dev.sh`, no flag):
  - The app behaves exactly as before. Walk a live board and force the offline
    alarm (stop the API) to prove it still fires.
  - A mock token presented to the real API is rejected.

Widths: 1440, 1024 (the primary operator target) and 390 (a floor, not a third
target), for the demo indicator and the "not in the demo" state at minimum.
Drive widths with `playwright-cli`. Do NOT use `chrome-devtools-axi` for width
work — it clamps at 500px and its `resize` silently no-ops while reporting
success. Confirm `innerWidth` before trusting any width claim.

Operational notes: `server/venv/bin/python -m pytest`, not bare `python`. The
migrator has `migrate` and `seed` only — no `reset`; seeding is the reset. STOP
THE API BEFORE SEEDING (CHEATSHEET §4). Unquoted globs in grep flags
(`--include=*.ts`) abort commands in this zsh — quote them.

Clean up after yourself: `.playwright-cli/` artifacts, scratch build output, any
recorded-but-unused fixture dumps.
